# 교차 검수 규칙

단계가 끝나고 프로젝트 검사가 통과한 뒤에 한다.

1. 검수자는 구현한 쪽의 반대 회사 모델이다(이 스킬 폴더 `MODEL_ROUTING.md`의 [검수]). 검수자는 **지적만 하고 코드를 고치지 않는다.**

   | 상황 | 검수자 |
   |---|---|
   | Claude가 구현, codex ✅ | `codex exec -C <워크트리> -s read-only -m <[검수] Codex 모델> -o docs/milestones/<이름>/runs/review-<단계>-<라운드>.md "<기준>"` 백그라운드 실행. `read-only`라 코드를 고칠 수 없다 |
   | Codex가 구현 | Claude 서브에이전트(`model`은 [검수] Claude 모델) |
   | Claude가 구현, codex ❌ | Claude 서브에이전트. 구현한 모델과 다른 모델을 쓰고(같으면 [판단] 모델), 구현 과정을 모르는 새 맥락에서 시작한다. 같은 회사 검수라 놓치는 게 더 많을 수 있으니 계획 파일 "검수 판정"에 `같은 회사 검수`라고 적는다 |

   Claude 서브에이전트 검수자에게는 "파일을 고치지 말고 지적만 한다"를 브리프에 넣는다. 2라운드에서는 1라운드 지적과 감독자 판정을 기준에 붙여 새로 실행한다.
2. 검수자에게 주는 기준은 닻의 완료 조건, 계획 파일의 이번 단계, 스펙, 검사 결과다. 질문은 하나다: "완료 조건 대비 나아졌고 어긴 것이 없나." 완벽함은 기준이 아니다.
3. 검수자는 지적마다 등급을 붙인다.
   - **차단**: 완료 조건·스펙 위반, 틀린 동작, 데이터 손실, 보안, 계획 밖 파일 변경
   - **선택**: 나머지 전부
4. 감독자는 지적마다 코드에서 직접 확인하고 확정/기각과 근거를 계획 파일 "검수 판정"에 적는다.
5. 확정된 차단만 수정한다. 선택은 "백로그"에 적기만 한다.
6. 감독자가 기각한 차단 지적은 근거와 함께 검수자에게 한 번만 다시 보낸다. 그래도 차단이라고 하면 사용자에게 올린다. overnight 모드면 닻의 "승인 대기"에 넣고 독립 작업을 계속한다.
7. 단계당 최대 2라운드. 2라운드는 1라운드 차단 항목이 고쳐졌는지만 본다. 새 지적은 새로 생긴 차단만 받는다. 2라운드 뒤에도 남은 확정 차단은 사용자에게 올린다(overnight면 승인 대기). 그 단계는 ✅로 바꾸지 않는다.
