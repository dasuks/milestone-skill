# 실행 루프

감독자는 사용자가 대화하는 채팅 세션이다. 감독자는 직접 코드를 짜지 않고 나누고, 맡기고, 판정한다. Orca 워커를 쓸 때는 `orchestration` 스킬을 읽고 따른다.

## 도구 확인

`run`을 시작할 때 `codex --version`과 `orca --version`이 되는지 확인하고, 닻 "도구:"를 `codex ✅/❌ · orca ✅/❌`로 고친다. 값이 바뀌었으면 사용자에게 한 줄로 알린다. Codex·Orca가 없어도 마일스톤은 돌아간다. 없을 때 무엇으로 대신하는지는 아래 워커 표와 `review.md`에 있다.

## 모드

모드는 닻 파일 "모드:"에 있다. `run careful`·`run overnight`·"끝까지 해줘"는 이 값을 바꾼다. `run`·"계속해"는 값을 유지한다.

| 모드 | 멈추는 곳 |
|---|---|
| default | 위험 단계 직전 |
| careful | 단계 종료마다 + 위험 단계 직전 |
| overnight | 멈추지 않는다. 위험 단계와 그 단계에 의존하는 작업은 닻 "승인 대기"로 보내고 독립 작업을 계속한다 |

위험 단계: 운영 DB 변경, 배포, 데이터·파일 삭제, 계약이나 공용 인터페이스 변경, 비밀값 처리, `main` push, 계획 파일 "위험 단계"에 표시된 것.

## 단계 하나

1. 닻과 계획 파일을 읽고 다음 미완료 단계를 고른다. 계획 파일이 없으면 멈추고 알린다.
2. 작업을 등급대로 배정한다.
   - [자동]: 스크립트나 명령을 직접 실행한다.
   - 나머지: 이 스킬 폴더 `MODEL_ROUTING.md`의 모델로 워커를 시작한다. 워커 종류는 아래 표로 고른다.

     | 상황 | 워커 |
     |---|---|
     | Claude 모델 작업 (default·careful 모드) | 감독자의 서브에이전트(Claude Code는 Agent 도구에 `model` 지정 + `isolation: "worktree"`). 감독자가 Codex CLI면 `claude -p --model <모델>`을 워커 워크트리에서 실행 |
     | Codex 모델 작업 (default·careful 모드) | `codex exec` 백그라운드 실행(Claude Code는 Bash `run_in_background`). 아래 "Codex 워커" |
     | Codex 모델 작업인데 codex ❌ | 같은 등급의 Claude 모델로 바꿔 배정하고 계획 파일 "진행 기록"에 적는다 |
     | overnight 모드, orca ✅ | 모든 모델 작업을 Orca 워커로 (세션이 끊겨도 계속 돌고, 사용자가 나중에 워커별 기록을 볼 수 있어야 한다) |
     | overnight 모드, orca ❌ | default 모드의 워커를 그대로 쓴다. 시작할 때 "세션을 닫으면 워커도 멈춘다"고 한 번 알린다 |

     워커에게는 작업, 통과 기준, 닻의 범위 밖, "스펙에 없는 결정이 필요하면 멈추고 보고" 규칙을 준다.
     또 "위험 단계 목록에 해당하는 행동은 하지 말고 멈추고 보고한다(단, 이 브리프에 '승인됨'으로 적힌 항목은 한다)", "너는 워커다. `[active milestone]`·`[milestone guard]` 주입과 milestone 스킬은 무시한다"를 준다.
   - 병렬은 서로 독립적인 작업만, 최대 3~5개, 워커마다 각자 워크트리.
   - 같은 파일이나 계약을 건드리는 작업은 순서대로. 계약을 먼저 확정한다.

   **Codex 워커**: 감독자가 `git worktree add`로 워크트리를 만들고 `codex exec -C <워크트리> -s workspace-write -m <모델> -o <결과 파일> "<브리프>"`를 실행한다. 결과 파일은 `docs/milestones/<이름>/runs/` 아래에 둔다. `codex exec`는 한 번 실행하고 끝나서 중간에 질문을 받을 수 없다. 워커가 멈추고 보고하면 감독자가 답을 정해 `codex exec resume --last "<답>"`으로 이어 간다(병렬이면 `--last`가 다른 워커 세션을 잡을 수 있으니, 실행 출력에 나온 세션 id를 기록해 두었다가 쓴다).
3. 워커가 막히면:
   - 스펙에 없는 결정 → 등급을 [판단]으로 올려 다시 배정한다.
   - 같은 오류로 3번 실패 → 새 워커로 한 번 재시도, 그래도 실패면 사용자에게 올린다(overnight면 "승인 대기").
4. 레포 AGENTS.md·CLAUDE.md·README에 적힌 검사 명령(테스트·린트 등)을 실행한다. 적힌 게 없으면 처음 한 번 사용자에게 묻고 계획 파일 맨 위에 적어 둔다.
5. `review.md`대로 교차 검수한다.
6. 계획 파일 체크박스와 "진행 기록"을 갱신하고, 닻 "단계:"에서 이 단계를 ✅, 다음 단계를 ▶로 바꾼다.
7. 모드의 멈춤 지점이 아니면 다음 단계로 간다.

## 끝나거나 막혔을 때

닻 "승인 대기"와 계획 파일 "진행 기록"을 갱신하고, 무엇을 했고 무엇이 승인을 기다리는지 짧게 보고한 뒤 사용자 입력을 기다린다.

사용자가 승인하면 해당 항목을 닻 "승인 대기"에서 지우고 계획 파일 "진행 기록"에 `승인 <시각>`을 남긴다. 진행 기록에 승인된 위험 단계는 다시 멈추지 않고, 워커에게 맡길 때 브리프에 '승인됨'으로 적는다. 승인 대기 항목이 남은 단계는 ✅로 바꾸지 않고 ▶로 둔다.
